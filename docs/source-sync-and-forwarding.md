# Source refresh and forwarded evidence

QuickBooks transaction capture and forwarded mail are background work. PostgreSQL owns the job state; the Cloudflare cron only wakes the Go worker. A queue acknowledgement or an HTTP response never marks a partial provider read complete.

## Local setup

Run all migrations in order, then start `docker compose up --build`. The API and worker share `DATABASE_URL` and `SECRETS_KEY`. The worker also needs the sandbox `QBO_CLIENT_ID`, `QBO_CLIENT_SECRET`, `QBO_REDIRECT_URI`, and `PUBLIC_APP_URL` to rotate short-lived QuickBooks credentials. Without QuickBooks OAuth, local accounting preparation and file upload still work; the transaction button remains unavailable until a hosted client connection is enrolled. The worker uses the existing on-demand scanner URL and `UPLOAD_SCAN_KEY` for forwarded attachments.

For a local mail test without Cloudflare, set `EMAIL_INTAKE_ADDRESS=evidence@your-test-domain` and a random `EMAIL_INTAKE_KEY` of at least 32 characters in the private `.env`. The protected internal endpoint accepts a MIME email only with this server key, an unexpired close-specific plus address, and one to five supported attachments. Do not expose `/internal/forwarded-email` publicly. The desktop Compose API has this route for local tests; the Cloudflare edge rejects public `/internal/*` requests. Local upload remains the easiest way to work without an email domain.

## QuickBooks workflow

On an enrolled sandbox close, confirm the company and request a transaction refresh. The API writes one idempotent active job for that close, connection, and month. The worker leases it, refreshes credentials when necessary, reads fixed transaction types and company preferences in bounded pages, and checks provider IDs, revision tokens, dates, duplicate rows, and capture size. It also compares a provider count before and after each transaction type and rechecks the Preferences revision at the end. A changed count, incomplete page, missing revision, changed settings revision, or over-limit type fails the whole job. It commits the JSON payload, read window, stable content digest, and linked evidence index together. Identical captures reuse the current evidence source. Changed captures retain the old JSON for history, mark older transaction evidence superseded, and return sandbox journal, VendorCredit, and Bill-correction approvals linked to it to preview. Uncertain attempts and linked pending production postings block replacement; production approvals are never reset by this sandbox refresh. Failed or interrupted jobs stay visible, retry at most three times, and never create a partial evidence source. Download the latest completed JSON to review individual provider records; the close binder records its digest and counts. These are sequential provider reads, not a transactional snapshot, ongoing change feed, or verified booked balance. A same-count edit between reads can still escape detection; refresh before relying on a prior capture.

In Source evidence, a ready PDF shows extracted page count. Printed `Page X of Y` labels are compared with that count; mismatches ask for review. An unnumbered PDF explicitly says page completeness is unverified. Repeated labeled invoice dates, numbers, totals, currency, or service dates with different values appear as review questions. Compare the original before confirming facts. A revised file retains a distinct digest and original; replacement requires a newer, fully extracted file with different bytes and an explicit reviewer reason. These checks do not choose the correct accounting fact or establish that an unnumbered source is complete.

The capture is explicitly requested, not continuous polling. A later scheduled refresh or webhook can enqueue the same durable intent only after its source authorization, scope, and cost are approved. A future Drive connector should use the same boundaries: exact selected files, a stored OAuth grant and revocation state, bounded inventory/cursor, immutable provider file ID and revision, a staged complete capture, copy-versus-revision comparison, quarantine/scanning, and a commit of the cursor only after evidence is durable. **Drive OAuth and syncing are deferred** until its permission path is approved; no Drive grant or broad-drive sweep is present.

Limits: 500 records per provider page, 2,500 records per transaction type and month, 12 MiB per completed capture, and 20 capture jobs per close. A capture above any limit fails visibly; it is not treated as complete evidence.

## Cloudflare email routing setup

Create a dedicated Email Routing address such as `evidence@your-domain` that routes to the edge Worker. Enable [Cloudflare subaddressing](https://developers.cloudflare.com/email-service/configuration/email-routing-addresses/#subaddressing) so `evidence+<issued-token>@your-domain` reaches the same route while preserving the token in `message.to`. Set staging variable `EMAIL_INTAKE_ADDRESS` to that exact base address and staging secret `EMAIL_INTAKE_KEY` to a separate random value of at least 32 characters. GitHub Actions sends both only to the edge/API container; the scan worker receives only scanner credentials. Deploy after all migrations and verify the Email Routing rule and domain in Cloudflare before issuing real addresses.

A reviewer issues an address in Source evidence, shares it privately, and may revoke it. Addresses expire after seven days. The envelope sender is recorded as **unverified** and never grants client authority. The Email Worker acknowledges only after the API commits the attachment rows; duplicate deliveries reuse the same rows. Supported direct MIME attachments are TXT/CSV up to 512 KiB and PDF up to 5 MiB, at most five files and 6 MiB of raw email. Nested forwarded `.eml` files and other types are rejected; ask the sender to attach the original supported document. Attachments remain quarantined while the on-demand ClamAV service scans their exact bytes. Only a current clean receipt permits firm download and release. Release requires a reviewer reason, creates or reuses the evidence digest, and starts the existing agent intake job. A changed file with the same name stays a separate source until the reviewer compares or explicitly replaces it.

For staging verification, send one synthetic two-attachment email to an issued address, confirm the rows move queued → scanning → clean, download and release one file, and confirm an agent proposal appears in Work. Retry the same email and verify no duplicate files. Revoke the address and confirm a further send is rejected. Confirm malware or scanner outages leave files quarantined. No client material should be sent before these checks pass in the deployed environment.
