# Client-specific QuickBooks sandbox onboarding

Connect a company to one organization/client and capture its account directory, bounded transactions and period reports. Connecting does not authorize a write: native corrections and [production posting](production-posting.md) require their own reviewed intents and grants. The legacy manually configured sandbox journal path remains separate.

## Configure once

1. Apply all outstanding [migrations](../infra/postgres/migrations/README.md#existing-database-upgrades). Stop API/worker during upgrades, retain a backup and restart matching revisions. Fresh Compose volumes apply every migration.
2. Create/configure an Intuit developer app for the **sandbox**, using its development client ID/secret. Register the exact HTTPS callback `https://YOUR_API_HOST/v1/quickbooks/callback`. For a same-origin Cloudflare deployment this is the application hostname; with a separate API URL it must use the API hostname.
3. Set server-only `QBO_CLIENT_ID`, `QBO_CLIENT_SECRET`, `QBO_REDIRECT_URI`, `PUBLIC_APP_URL` (the exact HTTPS SPA origin) and `SECRETS_KEY` (the existing 32-byte hexadecimal encryption key). Keep secrets out of frontend variables, logs and source control. The worker also needs the matching client ID/secret and encryption key for scheduled source refresh.
4. In GitHub's staging environment set `QBO_CLIENT_ID` and `QBO_REDIRECT_URI` as variables. Install `QBO_CLIENT_SECRET` and `SECRETS_KEY` directly in Cloudflare with `node scripts/cloudflare-credentials.mjs NAME staging < private-file`. The helper scopes them to API and worker; deploys preserve them. It checks partial configuration but does not provision an Intuit app or authorize a company.
5. Optional change hints: in the Intuit app's Webhooks settings, register `https://YOUR_API_HOST/v1/webhooks/quickbooks`, subscribe to the transaction and account entities, and set its verifier token as the server-only secret `QBO_WEBHOOK_VERIFIER` (API only). Each notification is checked with the `intuit-signature` HMAC and CloudEvents fields; it only records the event's change time on the matching active sandbox connection (notifications for production companies are ignored; their daily capture picks changes up), so a replayed or late notification does not repeat a capture that started after the change. An event dated in the future is refused; if clocks disagree, the daily refresh still picks the change up. The worker's scheduler, which runs every five minutes, then queues a fresh transaction capture for that client's unsigned current and prior-month closes, even inside the usual 24-hour window. A change that arrives during a capture queues another capture once that one finishes. Without the verifier the endpoint returns 503 and the daily refresh continues as before. A notification is a hint, not proof that the ledger is complete.
6. The operator needs an enabled WorkOS organization, `integrations:manage`, and access to the selected client (`clients:all` or an explicit client assignment). Local shared-token users can inspect the unconfigured state but cannot connect a real third-party account.

Local development without credentials still works for all existing preparation flows. The integration test mocks Intuit and uses synthetic PostgreSQL records. Interactive OAuth testing from local development requires an explicitly configured trusted HTTPS API/SPA endpoint, AuthKit and an Intuit sandbox app; do not weaken callback TLS checks for convenience. A tunnel is not provisioned automatically.

## Reading a client's production books

When a client's production QuickBooks company is connected and confirmed (under **Settings → Production QuickBooks authorization**, with the company name exactly matching the client), it becomes the client's books: account and month-end snapshots, transaction captures, Daily Books, exceptions and balance checks read it instead of any sandbox company. A sandbox capture queued before production was connected does not run, and sandbox captures stay as history but are no longer shown as current. The Evidence tab's **QuickBooks ledger evidence** panel then acts on the production company. Production reads are fixed GET requests; posting keeps its separate grant and approvals. Intuit change webhooks are registered per app and remain sandbox-only; production companies are checked by the daily scheduled capture.

## Connect and confirm

Open a client close → **QuickBooks sandbox ledger evidence**. Confirm the intended client and choose **Connect QuickBooks sandbox**. Intuit's accounting OAuth scope is broader than read-only; this application exposes only fixed GET operations through the new connection. Review Intuit's consent screen accordingly.

After consent, the API validates the unexpired attempt and redirects to the original close with authorization data in the URL fragment. The app removes that fragment and keeps the response in component memory. Choose **Complete authorization** while signed in as the initiating user. The backend rechecks the firm/client/user/state, records a durable exchange claim, consumes the state once, and encrypts the returned tokens.

Inspect the returned sandbox company name and realm ID. Connecting also reads the company's home currency and first fiscal month from its Preferences; the close page shows them, drafts in another currency are refused, and the year-end handoff follows that fiscal year. Currencies without two decimals (such as JPY) are not supported. Only then choose **Confirm this company belongs to the client**. A confirmed connection is shared across periods of that same case-insensitive client label within its organization. No client rename/merge capability is implied.

If the browser reloads before completion, authentication expires, consent is cancelled, or the ten-minute attempt expires, return to the client, disconnect the old attempt and start again. The app does not store authorization codes in local storage or infer approval from document content.

## Capture and inspect account records

Confirm **Capture account snapshot**. Expiring access tokens are refreshed through a durable claim; the latest rotated token is encrypted and saved before reads continue. The reader checks the confirmed company name, fetches active and inactive accounts, follows pages and saves only a complete bounded result. A failed page saves no snapshot. Read limits: 10,000 accounts, 2 MiB per provider response, 8 MiB combined accounts and 20 stored snapshots per close. Larger companies need a reviewed pagination/storage expansion.

The screen shows account count, company realm and capture time. Download the immutable JSON to inspect the account records. Provider decimal values remain JSON numbers without a floating-point conversion on the backend; snapshot hashes cover the canonical downloaded JSON. Third-party spreadsheet/JSON tools may round large numbers, so use decimal-aware tooling when inspecting financial values.

**An account-only capture is not a period-end ledger snapshot.** Account `CurrentBalance` values reflect the read time, pages are not transactionally consistent with each other, and no general-ledger transactions, trial balance or reports are fetched by the account-only action. The stored JSON explicitly records this scope and read interval. It is not automatically turned into preparation evidence, confirmed facts, booking proof or posting permission. Review packages include the captured JSON with its identity, digest and read times.

## Failure and recovery

- Failed reads show an error; previous snapshots retain their original capture times and are never relabeled fresh.
- A token exchange/refresh records `exchanging`/`refreshing` before Intuit is called. If the result is lost or persistence fails, reconnect. An interrupted process can leave that state visible; it is never blindly retried with an old refresh token.
- Company name changes require reconnection and explicit company confirmation. Disconnecting during a read prevents that read from saving a new snapshot.
- **Disconnect locally** removes stored tokens and stops new local use, while retaining snapshot history. Also revoke the app in Intuit to withdraw provider authorization. This application does not call the remote revocation endpoint yet.
- Losing `SECRETS_KEY` prevents decryption; restore the matching key. Do not substitute a new key and expect old ciphertext to work. Follow the [recovery runbook](operations.md).
- OAuth callback URLs carry short-lived codes: redact query strings in infrastructure access logs and disable analytics on callback paths. No application log intentionally records these values.

Live provider activation remains a separate, authorized sandbox exercise. Production OAuth and reviewed posting have their own setup in [production posting](production-posting.md); they never reuse the sandbox connection. Period report evidence is described below.

Primary protocol references: [Intuit OAuth client source](https://github.com/intuit/oauth-jsclient), [Intuit query builder](https://github.com/intuit/QuickBooks-V3-PHP-SDK/blob/master/src/QueryFilter/QueryMessage.php), [CompanyInfo entity identity](https://static.developer.intuit.com/sdkdocs/qbv3doc/ippdotnetdevkitv3/html/c3f4bf10-4ba7-c032-b2f0-db7deb1592f4.htm). CompanyInfo's object ID is distinct from the OAuth realm ID; access is addressed through the confirmed realm's API path.

## Period ledger evidence and coverage planning

Choose **Capture this month’s accrual reports and plan coverage** in the QuickBooks panel. Confirm accrual is appropriate for this client. The server takes the dates from the saved close month and reads `TransactionList`, `GeneralLedger`, `TrialBalance` and `ProfitAndLoss`, plus the account directory. Transaction List supplies reported transaction rows; this is not a raw transaction-entity synchronization. Cash-basis preparation, report-to-reconciliation CSV conversion and verified opening-balance rollover remain unsupported.

Report name, exact month bounds, accrual basis, currency, timestamp and report structure must be present and consistent. Empty reports need the provider's explicit empty-data flag. A failed report, invalid scope, indicated truncation, report above 8 MiB, or combined snapshot above 18 MiB saves nothing. Reports are sequential reads, not an atomic ledger state or proof of completeness. No arithmetic, sign inference or balance normalization is performed on provider cells.

A successful capture atomically stores the full snapshot and a named `.txt` JSON evidence source with its own content hash. For captures up to 96 KiB, the source contains the reports. Larger captures use an explicit index containing report sizes and a warning that report rows must be selected separately. The full report remains downloadable in QuickBooks and the close package. Each coverage proposal cites an account location; matching trial-balance rows also retain their JSON locations. Missing account identities in the trial balance are flagged for review. Bank/credit-card types suggest independent statement and ledger evidence; prepaid subtypes suggest invoice/schedule review; all other accounts require explicit accountant scoping. Inactive and zero-balance accounts are never silently excluded. Account-name text does not select accounting policy.

Open an account under **Coverage and client evidence**, then choose **Inspect account-matched ledger rows**. The server reads the immutable General Ledger report, selects rows under that exact account ID, and shows up to 20 rows per page with original JSON locations and cell values. A missing match is never treated as a zero balance. Choose **Add this page to agent evidence** to save a scoped, citable source. The agent can use it when an affected job is rechecked in Work; adding a page does not confirm facts or start posting. A new period capture supersedes selected pages from the prior snapshot. Report cells are context only: they are not full transaction entities, verified balances, or proof of a complete ledger. When the provider does not identify account rows unambiguously, inspect the downloaded snapshot and use supported manual evidence.

**Prepare this close** shows these deterministic coverage proposals without requiring AI credentials. They are proposed evidence needs, not an assertion that documents are absent or work is complete. Review the linked reports and current documents, upload the necessary supporting evidence, and use existing durable intake jobs. With OpenAI configured, those jobs inspect the permitted linked ledger evidence, select cited sources, ask specific questions and resume preparation after confirmed facts. Without OpenAI, existing local labeled-invoice proposals/manual preparation remain available; semantic report interpretation is not simulated. Reconciliation still requires two separate supported CSVs. Select unresolved requirements to draft one consolidated request, then approve its exact wording and recipient. Coverage resolves from the explicitly bound complete job set and current approved outputs; see [coverage requests and scanned attachments](coverage-requests.md). No request is approved or sent automatically.

**Month-end captures happen by themselves until a person takes one.** Once a close's month has ended everywhere (12 hours after midnight UTC, so a US afternoon on the last day never counts as month-end), the daily scheduled transaction capture also reads the month-end reports, as long as the close is not signed off and has no period snapshot a person took. It reads them again at most once every 20 hours after its last snapshot, and saves the new one only when its accounts or reports differ from that snapshot's (report times and current balances aside), so entries posted after the first capture reach the tie-out. A person's capture always wins: after it the schedule stops. At most six scheduled period snapshots are kept per close, and the schedule never takes a close's last free snapshot of the 20, so a person can always capture. When the schedule stops refreshing a close whose newest snapshot is its own (six taken, only the last free snapshot left, or the close is past the current and previous month with no active goal), or its latest month-end read failed, close readiness asks for a person's capture (or, after a failure, a successful read) before sign-off, because later entries may be missing. Scheduled captures use the same reads and evidence as a person's and are recorded as `scheduled-quickbooks-refresh`. Unlike a person's refresh, a scheduled one does not supersede earlier evidence or reset approvals. Work still cites the evidence it was prepared from, while the tie-out, flux and coverage read the newest snapshot, a coverage request drafted from an older snapshot is no longer current, and ledger pages can be selected only from the newest. If the read fails, it is logged and retried on the next scheduled capture; a person can capture at any time. Xero month-end captures run on their own schedule (daily, and early after a Xero change hint); see [Xero](xero-onboarding.md#capture).

A new capture supersedes earlier period evidence atomically, invalidates source-dependent review/posting approvals, and requeues pending OpenAI proposals. Uncertain sandbox posting attempts must be resolved first. The close-run scope digest includes ledger coverage, so a changed capture requires a fresh scope confirmation. Completed work is never silently overwritten; review source-changed drafts and recalculate using existing review controls. Historical snapshots and originals remain downloadable. A disconnected connection is labeled stale in coverage. Restore the connection and recapture before relying on it.

For a carried prepaid schedule, open **Refresh recurring prepaid work** after the new-period capture. It shows the matching prepaid Trial Balance row and expected schedule balance; the client accountant supplies and confirms the actual booked balance. The existing durable preparation worker then makes a source-linked revision for fresh review. The [carry-forward guide](carry-forward.md) describes the exact flow and limits.

Apply migration `021_ledger_selections.sql` after 020 before starting this API revision. No new dependency or cloud secret is required. Deploy the API and frontend together. Live sandbox validation remains pending; development integration tests intercept all Intuit HTTP calls.
