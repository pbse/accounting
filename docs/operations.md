# Operations and recovery

This is a runbook for the implemented controls, not an enterprise certification. Define owners, contractual retention, recovery objectives and escalation contacts before admitting client data. Deletion is always an explicit, admin-confirmed action; no automatic purge runs.

## Release and migration

Deploy the API and worker from the same reviewed revision. Fresh databases use all numbered migrations in numeric order; existing databases apply only unapplied migrations. Stop worker and API traffic before a schema change, preserve a verified backup, and restart them after migration and readiness checks. Migration 024 preserves unattributed historical email delivery events; investigate them, because they block close deletion for that firm. The GitHub staging job checks required schema objects but does not perform production migrations or grant deployment authorization. See [onboarding](onboarding.md).

A healthy HTTP process is not proof of a functioning worker. Check API `/readyz` for the schema/database boundary, point an outside uptime monitor at `GET /healthz/worker` (no sign-in, no firm data: HTTP 200 while the worker process and the workflow engine both beat within 5 minutes, otherwise 503 naming the stale loop; the worker sends platform alerts itself, so only this check notices a dead worker), and inspect the Work inbox for advancing durable state. Firm administrators can open **Firm operations and membership** or call `GET /v1/closes/operations` (`clients:all` and `operations:read`) for capacity, unattributed delivery-event counts, undelivered webhook counts and up to 100 aged/unknown preparation, attachment, email, posting and native correction (QuickBooks and Xero) alerts. Refresh after resolving items. An empty list is only a database snapshot.

To route operational alerts externally, configure an approved HTTPS `OPERATIONS_ALERT_WEBHOOK_URL` and optional `OPERATIONS_ALERT_WEBHOOK_TOKEN` as worker-only secrets. The default is disabled. The worker sends only organization ID, close ID, item ID, state and age in minutes; it never sends client names, documents, replies or calculations. Each alert state gets one durable attempt and an idempotency key. A 2xx response means the webhook accepted the notification, not that an on-call person acted. A timeout or non-2xx response becomes **unknown** and is counted in firm operations until the incident resolves; inspect receiver logs and escalate manually. There is no automatic retry. Configure the receiver and escalation policy before relying on paging.

The same webhook also receives **platform alerts**, marked `"scope":"platform"` with a `kind`, an `item_id` and a `detail`: `platform.loop_stale` (the worker process's or the workflow engine's heartbeat stopped for 5 minutes; the other job loops' stalls arrive as their firms' stuck items), `platform.runs_stuck` (workflow runs runnable but not picked up, as the admin panel's stuck view counts them), and `platform.unknown_effects` (provider writes waiting for reconciliation). Each problem is sent once, with the idempotency key `close-platform-alert/<id>`, and resolves when it clears; a new occurrence is a new alert. They carry no firm or client data. They run in their own worker loop, checked every minute, so firm alerts never delay them; a send interrupted before the webhook answered is marked unknown, like a firm alert's. A worker that is down cannot report itself: watch the admin panel's Overview, or point an uptime monitor at the API.

Each firm also has a daily model call limit, 2,000 calls per UTC day by default (`organizations.max_model_calls_per_day`, 1–100,000; migration 056). Every model call counts: document reading (the agent reserves one call, or two when it must first choose evidence from a large close), replays, plain-language Work requests and procedure drafts. At the limit the agent leaves a job waiting with the reason and retries it after 15 minutes, without using an attempt, so other firms' jobs keep moving. The person-started routes answer HTTP 429. The count is reserved atomically, so it never passes the limit. The limit counts calls, not dollars. Firm operations shows today's calls against the limit. Platform staff change it with the other caps under **Limits** in the staff console.

The default firm caps are 500 closes and 250 active preparation jobs. Close creation returns HTTP 429 when full; the database refuses new active jobs after the cap. Do not bypass either cap with direct inserts. Platform staff change the closes, active-job and daily model-call limits under **Limits** on the firm's page in the staff console (`platform:operate`, a reason, from the values shown; audited as `firm.limits`), after checking capacity and backlog. Archive and delete only under the firm retention policy.

## Enrollment, revocation and data retention

WorkOS owns identity, MFA and role assignment; the application records firm membership decisions. First enrollment needs a WorkOS organization token with `org:enroll`, `members:manage` and `clients:all`. Use the dashboard enrollment form; do not hand-enter an organization ID into client data. Member management uses the exact WorkOS `user_` ID, an authority reason and optimistic history version. Revoking membership blocks subsequent workspace API calls; revoke the WorkOS session and role as well. Firm suspension requires `org:manage` and blocks workspace access and future worker claims. A suspended firm's members are refused, so platform staff resume it after incident review on its page in the staff console (`platform:operate`, the typed firm ID and a reason); do not silently re-enable it.

For each close, a firm data administrator (`clients:all`, `data:manage`) records a retention date, optional legal hold and authority reference. `GET /v1/closes/{id}/retention` lists every known deletion blocker. Deleting a close also deletes its assistant conversations, and removing a member deletes theirs ([assistant](chat.md)). No date, a future date, a hold, active jobs/links/attachments/forwarding, uncertain email, posting and native correction attempts (QuickBooks and Xero), open posting grants, connected or shared QuickBooks, Xero or Stripe connections, an active procedure rule that depends on the close, and unattributed delivery events matching this close's sent messages block deletion. Unrelated provider events remain visible in the firm operations count but do not hold its closes. Historical attribution requires a reviewed, close-specific database correction; there is no bulk-delete or self-service override. Export the current binder or review package first if policy requires it. `POST /v1/closes/{id}/delete` requires the exact client/month, current retention version, approved reason and explicit confirmation. A single transaction removes this close's active database rows and writes a minimal receipt (firm, close ID, period, SHA-256 digest of firm ID, lowercased client name and period separated by zero bytes, production posting count, actor, reason, time). The receipt contains no client name. Deleting a close for contract termination or at the client's request also stops the client's [monthly hand-over](close-coordinator.md#every-new-month) and deletes the other names its documents use ([client memory](work-inbox.md#what-we-remember-about-a-client)), retired ones too. Provider records and previously exported copies remain outside this database. Backups may retain deleted data until the provider's separately configured expiry; record that expiry in the client agreement. There is no automatic backup purge or legal discovery workflow.

## Backup

Use the managed PostgreSQL provider's encrypted point-in-time backups plus a tested retention policy. Restrict backup access: database backups contain client documents, replies, audit records and encrypted provider payloads. Keep the encryption key in a separate recoverable secret store. A database dump without the correct `SECRETS_KEY` cannot recover encrypted connections or queued email payloads.

For an explicitly approved database, native PostgreSQL custom-format exports preserve the schema and data. Supply connection details through your secret manager/`PG*` environment; do not paste URLs/passwords into a ticket or enable shell tracing:

```sh
umask 077
pg_dump --format=custom --no-owner --no-acl --file=/secure/approved-backup.dump
```

The operator chooses the protected output location and retention. This example is not an instruction to export production data automatically.

## Restore without repeating external actions

1. Restore to a new isolated database; never overwrite the live database to test recovery. Keep all workers stopped and outbound provider access disabled.
2. Match the schema/application revision and restore required secrets separately. Confirm database ownership/permissions. Do not start an old application against a newer schema without a compatibility review.
3. Verify organization ownership, client assignments, source hashes, original documents, review/sign-off history, preparation jobs, scope records and provider receipts. Test two-firm denied access using the API before opening traffic.
4. Review all email and posting attempts against provider history **before enabling workers**. A backup can precede an external action that actually succeeded. Database state alone cannot distinguish this case. Stable email keys only deduplicate within the provider's finite window; an old backup can reset the recorded first-attempt time. Do not let restored queued emails run automatically. Keep delivery disabled until each uncertain record is reconciled. An email the provider's records show was sent is settled as accepted with its message ID, and an unknown one the provider never received as failed, by platform staff with `POST /v1/admin/firms/{id}/emails/{email}/settle` (`platform:operate`, the state seen, the provider evidence and a reason; audited as `email.settle`, also while the firm is suspended). **Settle** on **Stuck work** in the staff console does this for the unknown and stopped emails it lists. A queued email the provider has not received is left to send.
5. Preparation calculations can resume using their durable identities after source/readback checks. OCR and model requests may incur repeat work/cost after recovery; do not confuse that with a repeated ledger write.
6. Record actual recovery time and the latest recovered transaction time. Only a timed hosted rehearsal with provider reconciliation can establish the deployment's RTO/RPO. Neither target is claimed by this repository.

## Runnable local rehearsal

With PostgreSQL native client tools and a local administrative user:

```sh
PGHOST=127.0.0.1 PGPORT=15432 PGUSER=close infra/postgres/check-restore.sh
```

Use your own local port/user. The script rejects non-loopback hosts, creates two uniquely named temporary databases, applies all migrations, inserts two synthetic firms with same-named clients, dumps/restores, verifies source hashes and durable jobs/scopes, and removes only its own databases and dump. No API, worker or provider is started. The rehearsal proves schema/data recovery for those fixtures, not live credentials, backup scheduling or hosted recovery objectives.

## Security center

**Security** in the sidebar (`GET /v1/closes/security`) is one page for firm administrators (`clients:all` and `members:manage`; anyone else is refused):

- **People and their agents:** each member's latest enrollment decision (who decided, when, why), their recorded client assignments (labelled not in effect while the membership is revoked; firm-wide access comes from the WorkOS role), the agent (MCP) scope actually in force, shown apart from the latest agent access decision (a later request or decline never changes an approval in force), and pending invitations.
- **Connected services:** every QuickBooks, Xero and Stripe connection that is not disconnected, with the client, company or account, mode, state and who connected and confirmed it, each linked to the close page that disconnects it; the email sending connection. Google Drive grants are held by WorkOS per person and are managed there.
- **Posting authority in force:** only QuickBooks production and Xero posting grants that posting would honour now (unrevoked, unexpired, granted by a current member, on an active connection to the granted company), with their kinds, accounts, limit, expiry and granter, linked to where they are revoked.
- **Connector operations:** each QuickBooks, Xero and Stripe operation with how far it is proven and enabled here (PRD Appendix A): *documented*; *sandbox tested* when this firm has a verified record on a sandbox company (a QuickBooks correction, supplier credit or credit application made without a grant, the legacy sandbox prepaid journal, a sandbox QuickBooks read or a Stripe test-mode report); *production approved* when this server allows it (`PRODUCTION_POSTING_KINDS` or `XERO_POSTING_KINDS` for writes, the production QuickBooks or the Xero app for reads, and always for Stripe, whose key each firm holds); or *enabled* for the clients whose grant in force or active live connection covers it. It shows the last verified sandbox and live dates, each linked to the close that holds that record, who approves it, what a person does otherwise and one known limitation. QuickBooks accrual, loan, owner and Stripe-fee journals are checked in a sandbox, and Xero operations on a demo company, outside the app, so they say *not recorded in the app* rather than claim a check; a firm administrator can record such a check with its date and evidence (*Sandbox check outside the app*). Each operation also shows the firm's **accountant acceptance**: a dated record with its evidence, made by an administrator who reviews workpapers (`POST /v1/closes/security/operations`, migration `111_operation_acceptances.sql`), and withdrawable. These records are B06's release matrix (local and sandbox testing, production enablement, client grants and accountant acceptance, each dated); they never enable an operation, and an enabled operation without acceptance says so. Xero rows also say that journals need a connection authorized to post them, bill recodes one authorized to write invoices, and transactions the transaction scopes: the page does not open stored tokens to check scopes, and a connection made before those scopes were requested must reconnect.
- **What outside services receive:** OpenAI, Resend, QuickBooks, Xero, Stripe, Cloudflare, the text scanner, WorkOS and the operations webhook, each with what the code sends it and what shows it is in use here (for OpenAI, the model calls reserved in the last 30 days, which is a budget count rather than proof of delivery; OpenAI requests ask it not to store them). Document text sent to OpenAI (the documents the agent reads and the excerpts it selects from, PDF statement text for row proposals, policy text and reviewer edits for procedure drafts, and, when the firm turns on [written assistant answers](chat.md#written-answers), a close question and that close's saved reads) first has card, IBAN and Social Security numbers, labelled bank account numbers and sign-in details removed, as in [client replies](client-request-links.md); each model check of a quote or row runs on that same text. Stored files and extracted text are unchanged.
- **Recent changes:** the newest 100 recorded membership, client-access and agent-access decisions, invitations, connections, posting grants and revocations, email sending changes, and records an agent made for a member (evidence, preparation, close preparation, client request drafts, approval requests). It is derived from those histories and is not a complete audit trail.
- **Controls:** membership, invitations and operations; client assignments over every client; agent access decisions; and suspending the whole firm (`org:manage`, typing the firm's ID). Each keeps its own confirmation.

No credential, OAuth digest, token, webhook secret or value derived from one (such as a key's last digits) is ever returned. Members still request or give up their own agent access in Firm settings.

## Access and incidents

- Suspected firm exposure: stop provider activity and suspend the exact registered organization from the Security center (`org:manage`, typing the firm's ID and a reason) or through an authorized database change; preserve evidence. Application checks reject subsequent requests/claims. Already-running work and already-downloaded data cannot be recalled.
- Individual access: revoke app firm membership and client assignments, then revoke WorkOS membership/roles/sessions. A previously issued token is denied by the app's current membership check on subsequent requests.
- If every firm administrator is revoked, app enrollment will not silently reclaim the firm. Platform staff verify the exact person in WorkOS, then **Restore** them on the firm's People tab in the staff console (`platform:operate`, a reason saying how they were verified; audited as `member.restore`). Only someone the firm revoked can be restored, and their WorkOS roles are restored in WorkOS.
- Unknown external result: preserve the attempt and inspect provider canonical records. Never reset state to `queued` simply to make the dashboard green.
- Key loss: stop delivery, recover the matching key from secure backup and verify decryption on an authorized record. Do not replace it with a random key.
- Data removal: use the exact-close retention preview and deletion action; never bulk delete historical events to clear a blocker. Reconcile unresolved records and verify a deletion receipt plus absence of the exact close before reporting completion.

## Offline encryption-key rotation

Stop API, worker and deployment traffic. Preserve a verified database backup and the old key in a separate secret store. Set `DATABASE_URL`, the **new** `SECRETS_KEY` and the **old** `SECRETS_KEY_PREVIOUS` only in an isolated operator shell, then run `go -C services/backend run ./cmd/rotate-secrets`. The command locks encrypted QuickBooks, Xero, Resend and outbox records in one transaction, decrypts with the old key, encrypts and reads back with the new key, and commits only after every record passes. It does not contact providers. If it reports an uncertain commit, inspect ciphertext with both keys before retrying. Deploy the new current key to API and worker only after the rotation succeeds, verify a controlled provider read, then remove the old key from the operator shell. Never configure `SECRETS_KEY_PREVIOUS` on API, worker, Cloudflare or GitHub Actions.

## Row-level security

Migration 047 enables row-level security on every public table and makes every public view check it as the caller. Each statement from the API carries the signed-in firm (`app.organization`), so a query that forgets its firm filter still returns only that firm's rows, and a write into another firm fails. Token-checked public routes (client links, provider webhooks, the QuickBooks callback) and the worker run as system work and see every firm, which is what they need today. API work with neither a signed-in firm nor a system mark sees nothing.

Use a direct database endpoint, not a transaction pooler: the current adapter caches session-level tenant context on each connection. See [database setup and role grants](../infra/postgres/migrations/README.md#fresh-hosted-database).

Policies bind the runtime role only. Run migrations as the owning role and run the API and worker as a separate role that does not own the tables and has neither superuser nor BYPASSRLS; grant it `SELECT, INSERT, UPDATE, DELETE` on all tables and `USAGE, SELECT` on all sequences in `public`. Hosted `/readyz` (WorkOS configured) returns 503 when the runtime role would bypass the policies or any table or view lacks them. Local development connects as a superuser, so policies do not apply there. The key-rotation command marks its own transaction as system work.

Pending deployment checks include a configured/live-validated alert receiver, backup expiry verification, Cloudflare routing/configuration for the implemented scoped MCP server, and a hosted recovery exercise. See [deployment boundaries](deployment.md#production-and-remaining-deployment-work). Keep these gaps visible during any pilot review.

## Human effort measurement

The PRD's north star is total human minutes per supported close. Close-scoped screens (a close's sections, the review canvas and calculators opened for a close) credit 30 seconds of **tracked workspace activity** only when the tab is visible and someone used the keyboard, pointer or scroll in the last two minutes. The server caps credit at 60 seconds per person, close and minute, so extra tabs never add time. Nothing about the page content, keystrokes or URLs is sent. Reviewers add off-screen preparation, corrections or configuration on the close's **Close & sign-off** section. Waiting on clients (delivery to first reply, answered requests only) and delivered requests without a reply are reported separately from labor. **Measure → Human effort** shows each close in a month and the median across measured closes only; closes without activity read "Not measured", never zero. Raw per-person minutes stay in the database and are deleted with the close; the product shows only close-level totals. Our own team's assistance is not included and must be recorded separately. Each close also shows its recorded review decisions, how many came after an earlier version of the same draft was approved (following each revision's link back through unreviewed versions, for any reason, not only a changed source), and its review minutes; the month's totals of reviews and reviews after approval cover every close you can open that month, measured or not. Review minutes are estimates: a person's tracked minute counts once under its latest activity, and recorded minutes are dated when entered. Apply migration 039 with the API and worker stopped; `/readyz` checks it.
