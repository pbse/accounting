# Prepare this close

Large ready-evidence inventories now use a separate OpenAI selection pass before interpretation. The model sees source IDs, names, roles, byte sizes and short excerpts, then selects at most 20 sources totaling at most 128 KiB for a single preparation job. Selection cannot create accounting facts or approve work. The proposal lists every source it did not cite, including sources it may not have read in full, and the reviewer must inspect and acknowledge that list before confirming facts. Any change in the full close inventory invalidates the proposal. If a safe bounded set cannot be selected, the job stops with a clear error for manual scope review. This does not certify that all client records or QuickBooks transactions are present.

The global Work inbox can coordinate, recheck or stop work across closes, either for up to 10 checked closes or for a [portfolio goal](#portfolio-goals). The reviewer previews each close's current count and supplies a reason when stopping. Recheck returns only ready, current failed or pending proposals to evidence interpretation; it does not confirm facts or methods. Each close uses a snapshot-checked, permission-gated action; responses are shown separately because some closes can change or fail. Refresh and inspect a failed close before trying again. Prepared work and already-sent messages remain in history.

Apply migration 016 after migrations 001–015. The same API/database-backed behavior runs locally and in Cloudflare containers; there is no second queue or calculation engine.

1. Open a client/month and upload the available evidence. Each upload already owns one durable interpretation/preparation job. Local proposals use explicit labels; configured OpenAI interpretation uses the existing source/citation and confirmation controls.
2. Below upload, inspect the proposed document work types, questions and account needs, then confirm **Prepare this close**. These are candidates from available evidence, not a complete-record certification. The server checks the exact source and ledger inventory and records its actor, digest and source/job identities. Repeating the action on the same inventory returns the same run. Proposal progress alone does not change that inventory digest.
3. The run reads each original job's real status. **Next decisions** links directly to work needing confirmation, client follow-up or draft review. Follow a source link to Work to inspect proposed facts, resolve questions, approve a client request or confirm preparation. Repeated question wording is grouped, but answers are never copied between invoices automatically.
4. Approved replies resume their original jobs. Refreshing the browser or restarting the API does not create new jobs. The view polls every five seconds and reports errors instead of treating a failed read as success.
5. New or replaced source documents produce **scope changed**. Review the current list to record a new scope; earlier scopes remain in exported history. Existing jobs and answers are reused. Failed/cancelled/unsupported jobs stay explicit blockers and are handled in Work; the coordinator cannot bypass their authority checks.
6. **Drafts prepared — review required** means only these uploaded-source jobs have prepared current drafts without known blockers. Review the drafts and define/sign the separate supported close scope. Manual drafts, carried schedules, external ledger checks and missing documents are not inferred to be included.
7. The proposed work mix names each source's interpreted kind and shows the linked ledger coverage status. It is a review aid for the uploaded evidence, not proof that every client account or missing document was discovered.
8. To stop unresolved evidence jobs together, open **Stop unresolved evidence jobs**, give a reason and confirm. The server compares the current job snapshot, blocks while an approved client email is sending, revokes unused reply links and cancels those jobs. Completed drafts and accepted emails remain in history. A stopped job can be restarted individually from Work; its facts and evidence are interpreted again before confirmation. Refresh if the snapshot changed. Queued email delivery checks the revoked link before sending.

The Work inbox also offers a **Prepare selected closes** portfolio command for up to 10 checked closes. It previews each close's source count, submits the existing scope-checked action per close, and reports partial success separately. The existing **Stop unresolved work** command remains available. Neither command approves accounting facts, methods, requests, postings or sign-off.

**Ask Work** also accepts plain language ("what's stuck for Acme this month?") when the agent model is configured: only the request and the visible close labels are sent (unstored), and the model can only pick one of these commands for a visible close, which then runs through the same preview. Exact phrases never call the model. It understands bounded phrases such as “show blockers,” “show everything waiting on the client,” “show dependencies,” “why is Client · YYYY-MM waiting?” and “rehearse Client · YYYY-MM.” Prepare, recheck or stop for one visible close opens its per-close preview; any other target is a portfolio goal. The Work dashboard also lists up to 100 current workpapers whose source or inherited schedule changed, filtered to the signed-in user's client access. Open the close to revise and reapprove; the list never carries an earlier approval forward. The command shortcut uses these explicit phrases locally, without an AI credential or permission bypass.

## Portfolio goals

Type a goal in **Ask Work**, such as “prepare my clients due Friday”, “recheck failed work”, “stop work waiting on the client” or “prepare all visible” (migration 074). The server reads it without a model:

- **The verb** is prepare, recheck or stop.
- **my clients** (or mine) keeps closes you own.
- **due on / before / by** a day (today, tomorrow, a weekday, this week) or a YYYY-MM-DD date keeps closes due that day, earlier, or that day or earlier; plain "due" means by. Day names resolve from your browser's date.
- **waiting on the client** (or clients, replies) keeps closes with a job waiting on the client; **failed** keeps closes with a failed job.
- **all visible** keeps closes with work in the inbox's current view and client search, however many the inbox shows.
- Anything else is not a goal: Work hands it to its plain-language interpreter when the model is configured, and otherwise shows examples. Statement requests are not told apart from other client requests.

`POST /v1/closes/portfolio` selects the closes you can access that are not signed off, by due date, up to 100 (it says when more matched), and saves the goal with each close's name, current count and the digest the close page's own preview would show; a close with nothing to do is listed as skipped. The goal lists them with the selection in words and its resolved date. Confirming (and, to stop, a reason) runs `POST /v1/closes/portfolio/run`, which acts on at most ten pending closes per call; the browser calls it until none are left. Each close runs the close page's own prepare, recheck or stop, under your `workpapers:review` permission and current access to that close, with the saved digest, and its result is recorded in the same transaction: coordinated with the run number, already being prepared, rechecking or stopped, or the refusal (for example work that changed since the preview, a firm job limit, or access you no longer have), with none of a refused action's writes kept. A temporary failure (a read the action could not make) leaves the close pending and stops the run, so running the goal again retries it. A stop uses the first reason saved for the goal. Leaving the page stops only the calling; Work lists your unfinished goals (up to 5) to resume, and only you can see or run a goal. A close you can no longer access shows neither its name nor its result. Deleting a close removes its goal rows; removing a member removes their goals. The assistant, asked firm-wide for a goal it can read, links to Work with the goal filled in.

## Hand the close to the agent

Say **“Get this close ready for review by Friday”** in the close's assistant (or `/delegate Friday`, or **Hand it over** at the top of the Overview), check the card and hand it over (migration 081). Firm-wide, naming the client by any distinctive word of its name, and its month if you like (“Get Acme's September close ready for review by Friday”), links to that close's card, or lists the matching closes. A request with any other instruction in it (“… and use our approved procedures”) is not handed over: the reply names the words the agent does not act on, so nothing is silently dropped. Handing over needs `workpapers:review`; the due date is optional and editable on the card.

From then on the agent owns getting every uploaded document to a draft ready for review, whether or not anyone has the app open:

- About once a minute the worker brings new or replaced documents and client replies into preparation, recording the scope as a normal run started by “close goal #N for *owner*”. A scope that returns to an earlier run is recorded once.
- The goal card (in the assistant and at the top of the Overview) lists every current document by what it waits on, with the exact step and where to take it: **Needs you** (facts to confirm, questions to answer, a request to send, a partial reply to resume, an undelivered email, a failed or blocked draft, files to release), **I can't prepare** (unsupported work, with the agent's question), **Waiting on the client**, **I'm working on**, **Ready for review** (with its drafts) and **Left out** (stopped documents). It says when the result covers uploaded documents only, and the due date with days left or overdue.
- When every current document that is not stopped has a current draft without blockers, changes requested or a changed source, a review goal is **reached**: the owner's Attention shows it and the card links the drafts. New work puts the agent back on it; it keeps watching until the close is signed off. (A sign-off goal goes on, [below](#finish-line-ready-for-review-or-signed-off).)
- **What happened** lists the goal's own steps with everything people and the client did since it started: confirmations, answers, approved, delivered and emailed requests, link, email and recorded replies, review decisions and rechecks. The card shows the newest 50 and **Show all** reads the rest (`?activity=all`). Every goal and its full history are in the close package's work history.

### Finish line: ready for review or signed off

The card asks where the agent's job ends (migration 082): **every document has a draft ready for review** (above), or **the close is signed off**. “Get this close signed off by the 10th”, “… sign-off …” or “Close the books by Friday” proposes sign-off (“the closed month” or “hand it off” does not); the card can change it either way, and firm-wide links keep the choice. A day of the month (“by the 10th”) is the next such date, here and in portfolio goals.

A sign-off goal records the review-ready point once, as a milestone (`ready_at`), and keeps going:

- each unapproved draft becomes **Review and approve draft #N**;
- once every document is ready (or a sign-off stands), **Sign-off** lists what the close's readiness still blocks on that is not a listed document (the sign-off scope, required drafts, coverage, external steps, work on replaced documents, uncertain posting or correction attempts), with a link to the sign-off tab, where a person defines the scope and signs off;
- every approved draft that proposes an entry shows where each of its postings stands (one line per provider): not posted in the app (post it from the draft, or book it in the ledger and record that as an external step in the scope), approved to post, approval expired, outcome unknown, or posted and confirmed by its readback with the provider's reference. An entry that is not posted does not block, because the firm's scope decides what sign-off covers;
- with nothing left, **Ready to sign off** links to the sign-off tab (`close:signoff`).

The goal is reached while the sign-off stands (the close's readiness says signed off): the card says who signed off and links the signed binder on the sign-off tab and next month's close once one exists. If something changes after the sign-off, the goal waits, prepares nothing, and says the close needs reopening; once a person reopens it, the agent is back on it. A review goal still stops at sign-off. The history also shows the sign-off scope, sign-off and reopen decisions, and posting attempts and readbacks. “Signed off” is the firm's sign-off of the scope it defined, not a claim that every entry was posted.

### Every new month

Tick **Do this every month for <client>** on the hand-over card to hand over each new month the same way (migration 083). The card first says exactly what that means: from which month (the one after the close, or the current month when the close's month ended earlier; months that ended before are not new), the finish line, and the monthly due date, which keeps the card's due date's distance after the month ends (at most 60 days), or **no due date** when the card has none or it falls inside the month. A client has at most one monthly hand-over; the card shows an existing one instead of the checkbox.

When a month ends (UTC), the worker opens that month's close for the client if it does not exist yet (counting against the firm's close limit, as when a person opens one) and hands it to the agent under the member who set it up, unless the close is signed off or already handed over. Each month is handled once and in order, so none is skipped: a goal a person stops, or a close someone deletes, is not redone. At the firm's close limit the routine waits, says so on the card, and tries again each minute, the least recently tried routines first; later months follow once there is room. The goal card and the Overview show the monthly hand-over, the next month it will take, and **Stop the monthly hand-over** (a reason is required; months already handed over keep their goals). It also stops when the member who set it up leaves the firm or, if their access came from an assignment to the client, loses it; and when a close of the client is deleted for contract termination or at the client's request. A member with firm-wide access keeps that access in the WorkOS role, which the worker cannot see; any reviewer can stop the routine.

### Hand a document to a teammate

A document that needs a person to look into it (facts to confirm or a question to answer, a failed or unsupported document, a draft that needs changes) can be handed to a teammate from the goal card (migration 084). **Hand to a teammate** lists, by name, the firm's members other than you who can review the client's work: their WorkOS roles together hold `workpapers:review` and either `clients:all`, or they are assigned to the client. An optional note (up to 500 characters) says what to look into. Sending a client request and approving a draft are not handed this way; they need their own permissions. A signed-off close must be reopened before work is handed out.

The teammate finds it in **Attention** under **Documents handed to you**, linked to the document alone in Work (with **Show all work**), and the card shows who has it ("With you" for them). They act through Work with their own permissions. The agent closes the hand-off once the document no longer needs anyone (it is prepared, waits on the client, or is stopped), keeps it while the document is read again after an answer, and takes it back when the teammate leaves the firm or loses the assignment their access came from; signing the close off or stopping the agent closes it too. The goal's history shows each hand-off and how it ended. Anyone who can review the close can **Take it back**, and the teammate can **Hand it back**; a document is with one teammate at a time. Only the local development firm, which has no WorkOS, lists every member; a hosted firm without WorkOS lists nobody rather than people it cannot check. A role change in WorkOS alone is not seen by the worker; take the document back.

The agent never confirms facts, answers questions, approves or sends requests, approves drafts, posts or signs off, and it calls no model: those stay with people through their existing screens and permissions. Recording the preparation scope is preparation the firm lets agents do on their own, so it is attributed to the goal, not to a person, and no approval rests on it. Anyone with `workpapers:review` can **Stop the agent** with a reason; work already started keeps running (use **Stop unresolved work** to stop the work itself). A review goal stops by itself when the close is signed off (reopen the close to hand it over again); any goal stops when its owner leaves the firm. A suspended firm's goals wait, and a goal whose step fails is retried after the others. The owner's WorkOS role is not visible to the worker, so a role change alone does not stop a goal; any reviewer can stop it.

`GET /v1/closes/{id}/goal` returns the latest goal, its live progress and history; `POST /v1/closes/{id}/goal` (`confirmed`, optional `finish` of `review` or `signoff`, default `review`, optional `due_on` from today to a year ahead, and optional `every_month`) hands over; `POST /v1/closes/{id}/goal/stop` (`reason`, 1–500 characters) stops it; `POST /v1/closes/{id}/routine/stop` (`reason`, 1–500 characters) stops the client's monthly hand-over. `GET /v1/closes/{id}/people` lists the teammates a document can be handed to; `POST /v1/closes/{id}/goal/handoffs` (`job_id`, `assignee`, optional `note`) hands one over and `POST /v1/closes/{id}/goal/handoffs/{handoff}/take-back` takes it back. One goal per close is open at a time. Deleting the close deletes its goals.

This close-level coordinator preserves existing per-document interpretation and request/reply routing. Coverage requirements support consolidated client requests and scoped replies through the same durable jobs; see [coverage and attachments](coverage-requests.md). It does not infer complete account coverage or autonomously approve accounting methods. One consolidated visual question list is not a consolidated delivery authorization. Delivery still requires its own explicit authorization.

## Ledger coverage

Capture period evidence from the QuickBooks panel to see account-level coverage proposals and report row references below the preparation progress. Exact account-name or ID facts in document proposals suggest candidate job bindings; the reviewer confirms the complete job set and exclusions. Accrued-looking current-liability accounts are candidates for accrual evidence, not certified accruals. Proposed source references can search the captured General Ledger within an exact account ID. Search scans the stored report once, keeps original row locations, and returns pages of 20 rows that can be saved as cited evidence. A name or text match never certifies completeness, a balance or accounting policy. Coverage resolves only after bound jobs have approved current drafts. New ledger evidence changes the run digest and supersedes source-dependent approvals; see [the period flow](quickbooks-onboarding.md#period-ledger-evidence-and-coverage-planning).
