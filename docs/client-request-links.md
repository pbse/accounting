# Private client request links

The original text reply loop is now extended with [consolidated coverage requests and scanned attachments](coverage-requests.md): approve a request → issue a private link → share it manually → receive the original reply → resume the same preparation job → review proposed facts again.

## Reviewer experience

In Work, approve the exact recipient and wording using the existing request review. Choose **Create new private reply link**, copy the URL while it is visible, and share privately with that approved recipient through your authorized channel. Creating a link does not send email or claim delivery. Sending requires the separate [email approval](email-delivery.md).

Links expire after seven days. **Revoke reply link** invalidates a link immediately, including one that already has a reply (it would otherwise keep taking additions); creating a replacement, a retry or a close-wide recheck or stop also revokes the job's links. The raw secret is shown only at creation and is not recoverable from the database. A lost creation response can be resolved by issuing a replacement.

The link exposes only the approved request wording, client label and period. It cannot open workpapers, source documents, other requests or the firm workspace. By default anyone holding it can read and reply, so it suits requests where possession-based access is appropriate.

**Passcodes.** Under **Firm → Client link passcodes** (org:manage; any user in local development), a firm can require an 8-digit passcode on every link issued from then on (migration 057). The person who issues the link sees the passcode once: when creating a manual or consolidated request link, or when approving the request email. They tell the client by phone or in person. The app never sends it, and the email only says a passcode will be given separately. The database keeps only a digest salted by the raw link, which it never holds. The client page asks for the passcode before showing anything. A missing passcode answers `PASSCODE_REQUIRED`, each wrong try is counted on its own, and the fifth wrong try revokes the link. Replies and attachment scan retries need the passcode too. A reminder reuses the original link and passcode. A lost passcode cannot be shown again, and a retried email approval says so instead of reporting success: issue a new link, which revokes the old one. Links issued before the setting was turned on keep working as they were issued. Each change records the resulting state of both firm policies (independent review and passcodes), with its reason. Client accounts and app-sent one-time codes are not provided.

A request takes its first reply only while its work is as approved: the drafts its wording came from are unchanged as review reads them (not reviewed again, revised, or given a replaced source), no document its work was read from was replaced, and its job still waits on this request; a consolidated request also needs its ledger capture, coverage and target work unchanged. Other evidence the close gains, such as another upload, a transaction capture or a reply to another request, does not stop it (migration 091). Otherwise the client is told that the work behind the request changed and to contact the firm. Use **Withdraw request and recheck evidence**, review the new proposals, and approve a fresh request. Old links stay unusable. A request approved from drafts before migration 091 did not record their state, so it takes no first reply; issue a fresh one. Cancelling a preparation also stops replies. Link and request history remain in the close export, without secrets or their hashes.

## Client experience

The client opens the link without creating an account and sees the approved request as its numbered questions (a question continues until a blank line; a request without numbered lines is one question), with the full approved wording available beside them (migration 078). For each question they write an answer, tick **I'm attaching the document with this reply** (recorded as answered, naming the files) or tick **I'll send the document later** (each with an optional note), and they can attach documents. They can send some answers now and the rest later, on the same link, from any device: the server keeps each question's current answer and shows it back with its state (answered, waiting for your document, not answered yet). Original wording is preserved, including whitespace, except for sensitive values, which are removed before anything is stored (below). An identical retry is recognised by its receipt (from the redacted answers and the files) and is not saved twice.

Every reply with answers is saved as one document listing each question with its current answer, "Will send the document later" or "Not answered yet", and it replaces the client's previous reply document, which stays in history: preparation reads only the current answers, and a draft that cited the earlier reply is reviewed again, so a correction goes through the firm's review. Documents sent alone leave the reply document as it is. Work resumes on its own only when every question is answered; a partial reply waits, and Work shows how many questions are answered or awaiting a document with **Resume now with the partial reply**. After the first reply, the link (or a replacement the firm issues) keeps taking answers, documents and corrections until it expires or is revoked, while the work the request was approved for is still open (not completed or cancelled) with no newer request, and a consolidated request's coverage has moved only by the request's own progress. That progress never closes it: work started from documents the firm released from it may finish, and that work may be bound to its accounts. A request for accounts alone covers no approved work, so it keeps taking them while its coverage holds. An emailed reply the firm released counts as a reply too, so a replacement link issued after it takes follow-ups. The page tells a client sending a document they promised to tick “I'm attaching the document with this reply” on its question. A complete reply with an answer that is an attached document resumes work only once none of the request's documents still waits for its scan or release, so the last release resumes it; a complete reply answered in text resumes at once. Otherwise the client is told to contact the firm. The first reply still needs the request exactly as approved. Resending the latest reply is always confirmed; the firm can revoke a link with a reply at any time. Releasing a client attachment does not resume work waiting on a partial reply. Reminders stop once any reply arrives. Each question is answered, marked as a document to follow or not answered yet; a question needing clarification gets a new request. A plain text reply answers a request with one question; a request with more than 50 numbered questions is answered as one.

**Sensitive values are removed from every text reply** before storage: link replies, email replies (while still held) and replies or answers recorded by staff. Removed are card numbers (13–19 digits written together, in groups of four or in American Express 4-6-5 groups, passing the Luhn check; two dates side by side are never read as one), IBANs (valid check digits, any case), US Social Security numbers written ddd-dd-dddd, and bank account numbers of 6–20 digits written after a bank label ("checking account", "account number", "acct #"). A password, passcode, PIN, one-time or verification code, security answer, username, user ID or login label followed by ":", "=", "is" or "was" removes the rest of that line. Each removal leaves a marker in the text, such as "[card number ending 4242 removed]", so reviewers see where and what kind. The original is never stored, and no one receives it: not reviewers, not exports, not the model. Receipts and duplicate checks use the redacted text, so no fingerprint of a removed value is kept either. Email duplicates are recognized by sender, Message-ID, Date and redacted text; two identical emails carrying neither header count as one. The client is told what was removed, also on a retry. Routing numbers, SWIFT codes and ledger account references such as "account 6010" are left. Uploaded files are not changed, because statements legitimately carry account numbers; the same values are removed from document text before it is sent to the model ([operations](operations.md)). For removed values this supersedes the PRD's COM-02 clause on storing the original reply: COM-01 requires such a thread to be redacted and restricted. Replies stored before this change are not rewritten.

Replies and held emails are shown only inside the close, to people with that client's access or firm-wide access, like every close route.

A complete reply creates source evidence and a linked work reply atomically with returning the existing job to `waiting_evidence`. The worker uses the configured interpreter or local labeled-field parser. New facts still require human review and existing accounting confirmations. A reply never approves treatment, posting or firm sign-off.

Clients can attach PDFs through Cloudflare scanning and TXT/CSV through the separate on-demand ClamAV scanner. Mandatory malware scanning and firm release precede preparation; see [setup and limits](coverage-requests.md). Single-job and consolidated requests use the same approved Resend outbox, signed delivery tracking and individually approved reminders; see [email setup](email-delivery.md). Client accounts and verified-recipient authentication remain pending.

## Local setup and API

Apply `infra/postgres/migrations/009_client_request_links.sql` after 001–008 and restart the API. Fresh Compose databases apply it automatically. Existing volumes can use:

```sh
docker compose exec -T postgres psql -U close -d close -v ON_ERROR_STOP=1 < infra/postgres/migrations/009_client_request_links.sql
docker compose up -d --build api worker
```

Text replies require no new secrets. Attachments additionally require migration 018 and the Cloudflare setup described in the linked guide. Local development retains the private workspace token; hosted reviewers use the existing organization boundary and `workpapers:review` permission. Cloud activation and HTTPS deployment remain separate.

- Existing authenticated work actions add `link` and `revoke_link`, with current `revision` and approved `request_id`, and `resume` (work waiting on a client who has replied).
- `retry` on unanswered requests withdraws access and resumes evidence review.
- `GET /v1/client-request` reads a scoped request; `POST` submits `{body, confirmed:true}`.
- Public request calls authenticate using the link token as an Authorization bearer token. They never accept client/job/request IDs from the client.
- The browser receives the secret in a URL fragment, removes it from the address bar, keeps it in memory, and uses no-referrer/no-store requests. Refreshing the page requires reopening the original link. The client route does not initialize AuthKit.
- PostgreSQL stores only a SHA-256 token digest and issuance, expiry, revocation and consumption records. Go's `crypto/rand.Text` supplies at least 128 bits of entropy. Atomic row locks serialize reply, replacement, revocation and workspace actions.

The handler and existing staff reply capture reuse one evidence/queue writer (Ponytail rung 2). Randomness, hashing and HTTP use the standard library (rung 3); the UI uses native forms (rung 4). No client portal framework or second workflow engine was introduced.

## Verification boundary

`TestScopedClientReplyResumesJob` covers issuance authority, scope, rotation, revocation, expiry, stale context, exact original preservation, idempotent replay, receipt, resumption and withdrawal. Existing coordinator, agent and package checks cover the direct consumers. Live delivery, hosted access and model accuracy remain unverified.
